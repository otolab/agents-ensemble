# ADR 0083: operator-agent の session report 調停と利用機能の境界

- Status: proposed
- Date: 2026-11-17
- Related: [Epic #748](https://github.com/otolab/agents-ensemble/issues/748), [Issue #741](https://github.com/otolab/agents-ensemble/issues/741), [Issue #745](https://github.com/otolab/agents-ensemble/issues/745), [Issue #736](https://github.com/otolab/agents-ensemble/issues/736), [ADR 0037](0037-operator-agent-session-watch-and-dispatch.md), [ADR 0038](0038-operator-agent-conversation-report-hold.md), [ADR 0078](0078-operator-agent-session-report-coalescing.md), [ADR 0080](0080-operator-watch-state-lock-transaction.md), [ADR 0081](0081-operator-watch-pending-report-handoff.md), [ADR 0082](0082-operator-watch-acknowledgement-retry.md)

## Context

Issue #741 の目的は、複数の Issue session から細かな報告が続く状況で、オペレータが必要な報告や判断待ちの質問を見失わず、通知の turn 数も抑えられるようにすることにある。

Issue 本文と @otolab の追加コメントには、少なくとも二つの利用目的が含まれる。

1. **session に集中する** — 対象 session の報告を見つけやすくし、対象外 session の通常報告による割り込みを抑える。対象外の報告も後から届ける。
2. **手が空いたときに停滞候補を把握する** — 稼働 session の状態を低頻度で確認し、長く変化が見えない作業を確認候補として知らせる。

inq-7 の operator 承認で [Epic #748](https://github.com/otolab/agents-ensemble/issues/748) を追加し、native hierarchy を Epic #748 → [Issue #741](https://github.com/otolab/agents-ensemble/issues/741) → [Issue #745](https://github.com/otolab/agents-ensemble/issues/745) とした。inq-6 で決めた境界は維持する。#741 は session 単位の集約・focus・Open Question 優先・continuation hint 等の共通 scheduler、#745 は idle 候補の生成・対象判定・根拠・通知 gate・重複抑制を扱い、共有 pending report と dispatcher に依存する。idle の要件は #745 に残し、重複する作業 Issue は作らない。具体設計は提案段階で、本 ADR の Status は `proposed` のままとする。

## 現行契約（調査時点で確認）

### 集約・選択順・時系列

- [ADR 0037](0037-operator-agent-session-watch-and-dispatch.md) の基本選択順は、TTY user input、Open Question report、直前に dispatch した session の一回限りの continuation、その後は到着順である。
- [ADR 0078](0078-operator-agent-session-report-coalescing.md) は report source の粒度と同一 session の debounce / batching を置き換えたが、[ADR 0037](0037-operator-agent-session-watch-and-dispatch.md) の一回限りの continuation は置き換えていない。現行選択は、**TTY user input → ready な Open Question report を含む session → continuation が未消費で、直前 session が ready ならその session を一度選択 → それ以外は ready になった session の到着順**となる。Open Question の判定は report type によるもので、新規・未回答だけに限定されていない。
- report は `conductorAgentId` 単位で同じ dispatch source に入る。同一 session の queued report は、その session にある全 report の debounce deadline が満了してから、到着順を保った一つの `agent.send` にまとめる。他 session は独立して ready / dispatch できる。
- したがって現行の Open Question 優先は**session 選択時の優先**である。同じ session にある古い通常 report を Open Question が追い越す動作ではない。session 内の時系列を保ち、同じ batch に含める。

### deadline、hold、再起動と retry / ack

- pending report の `readyAt` は保存され、peer process の回収・再起動後も元の debounce deadline に使われる（[ADR 0081](0081-operator-watch-pending-report-handoff.md)）。旧 state に `readyAt` がない report は即時 ready として replay する。これは既存の `readyAt` 契約であり、新 state で保持する `firstQueuedAt` と、旧 state の `queuedAt` に migration / backward-compatibility を設けない判断とは別である。
- `readyAt` は現在の debounce deadline であり、最初に待ち始めた時刻を表す不変の age anchor ではない。新着 report や conductor-message quiet window により同一 session の待ちが延びる。現行契約には hard deadline がないため、連続更新中の session に最大待機時間は保証されない。本 ADR では、後述のとおり `firstQueuedAt + batchMaxWait` を追加し、batch を ready にする時刻に限って上限を設ける。
- continuation の選択状態は `run-operator-agent` の process 内 `dispatchState` にあり、再起動時に復元されない。focus 機能は未実装である。`operator-agents.config.yaml` の現行 profile schema に scheduler 設定もない。
- 現行 run loop は `agent.send` が結果を返した後、成功・未完了を問わず選択 batch の session key を continuation state に記録する。未完了 report は同じ ID で queue に戻るため、continuation が「最後に正常完了した session」ではなく「最後に send を試みた session」を指す場合がある。
- manual hold と conversation hold は OR で作用し、どちらかが有効なら全 watch report を保留する。`release_reports` は manual hold だけ、`/resume-watch` は conversation hold だけを解除する。hold 中も watch は続き、解除後に既存の batching 規則で再開する。hold は永続化されず、再起動後は解除状態から始まる（[ADR 0037](0037-operator-agent-session-watch-and-dispatch.md), [ADR 0038](0038-operator-agent-conversation-report-hold.md)）。
- 現行 queue は hold の開始・解除で `readyAt` を停止・再計算しない。したがって hold 中に debounce deadline が過ぎた report は、hold 解除後すぐ選択可能になる。
- 未完了 send は同じ report ID で通常 retry する。send 成功後の ack failure は send を重ねず ack のみ retry し、上限後または再起動後は同じ ID が再送される可能性がある（[ADR 0081](0081-operator-watch-pending-report-handoff.md), [ADR 0082](0082-operator-watch-acknowledgement-retry.md)）。delivery は at-least-once であり、重複はあり得る。
- profile 単位の SQLite transaction lock は state 更新を直列化するが、取得失敗後の再試行や process 停止、send 中断を越える end-to-end の通知時間は保証しない（[ADR 0080](0080-operator-watch-state-lock-transaction.md)）。
- `session.observe` が提供するのは Open Question snapshot と session statusLine で、worker の実行中状態や進捗 heartbeat ではない。保存済みの `running` phase や古い statusLine だけでは、正常な長時間処理と停滞を区別できない。
- 調査時点の operator-agent process は `agent.send` 実行中、dispatch queue の pending user input 数と conversation hold、TTY prompt の表示状態を個別に把握していた。TTY prompt 表示は入力欄が見えることを示すだけで、未送信入力や入力中かどうかは分からず、それだけで gate を立てない。調査時点では focus state と idle candidate generator は未実装だった。`session.observe` が返す OQ snapshot / `statusLine` や保存済み phase は worker の現在の実行状態・heartbeat を示さない。一般的な worker wait、正常な長時間処理、未確定 TTY 入力は推測しない。

## Decision（ADR 全体は proposed。指示済み条件と未決事項を区別）

### 共通コアと責務境界

**提案:** 新しい独立 queue や ack 経路は作らず、既存の durable pending report と dispatcher を拡張する。データの流れは次の形を基本とする。

`watch / 機能別候補生成 → 正規化済み report → 既存 pending state → 既存 dispatcher → agent.send → report ID ごとの ack`

- 正規化済み report は report ID、session / Issue identity、種別、本文、到着順を持つ。scheduler state は `arrivalOrder`、`firstQueuedAt`、idle candidate 用の `eligibleAt` と priority、send retry 用の `retryReadyAt`、凍結済み membership の `frozenBatchId` / `frozenPayload` を pending report ごとに保持する。priority は session batch の選択に限って適用し、同一 session 内の到着順は変えない。
- dispatcher は正規化済み report の session 集約、選択順、待機制御、hold、既存の retry / ack を担う。focus や idle 候補の判定ロジックを dispatcher に重ねない。
- idle 候補機能は対象 session の判定、観測根拠、fingerprint による重複抑制を担い、候補を通常 report と同じ lifecycle に載せる。現行 observation で確かな実作業停滞を判断できない限り、「停滞」と断定せず確認候補として知らせる。
- **作業単位（inq-6 / inq-7 オペレータ承認済み）:** Epic #748 の下に #741、さらに #745 を置く。#741 は共通 session scheduler、#745 は idle 候補生成・抑制を扱う。#745 は #741 の共有 scheduler / dispatcher が提供する通常 report lifecycle に載せる依存機能であり、別 Issue 化によって独立 queue / ack 経路を設けない。#745 の受け入れ条件には、inq-13 で承認された idle-only batch の通常 FIFO 帯への昇格と、通常 report の継続流入に対する公平性、inq-14 で承認された「生成/dispatch gate 通過後に scheduler で選択可能となった時点」を aging 起点とすること、inq-15 で承認されたeligible後のmanual hold中も時計を進めること、inq-16 で承認された observable conversation / focus gate 中の候補生成・scheduler 投入抑止と解除後の一回限りの現状再評価、inq-17 で承認された live OQ 単独では候補生成を抑止せず他 gate 解除後も OQ が live なら候補化できることを含む。抑止中の候補は蓄積せず、追いつき通知もしない。manual hold 中は既にeligibleな候補を送信せず時計だけ進め、解除後は経過 age で昇格を判定し、他の hold が残る間は dispatch しない。実装では明示的な send / pending user / conversation hold / focus state を gate に使い、TTY の未送信 buffer や一般的な worker wait は推測しない。候補生成が gate で抑止されている期間は aging せず、観測から候補生成・dispatch までに有限上限があるとはしない。hold / 停止 / 再起動時の pending 候補・重複抑制状態と at-least-once の重複可能性も利用者向け文書で説明する。

### Open Question と同一 session の順序

**オペレータ回答済み（inq-1 / inq-3 / inq-5 / inq-12 / inq-17。ADR全体は引き続き `proposed`）:** 同一 session 内では report の到着順を維持し、後着の Open Question で先行する通常 report を追い越さない。live OQ があることだけでは idle candidate の生成を抑止せず、他の conversation / focus gate が開いて idle 条件を満たせば、OQ report と同じ session batch / send に到着順で含める。focus が off のときは、ADR 0037 の順序に沿って TTY user input、Open Question を含む session、直前に扱った session の一回限りの選択ヒント、到着順の順に扱う。focus が on のときは、focus session の batch を report の種類にかかわらず focus 外 session の batch より先にする（`focus_all_reports`）。focus が有効な間は明示 focus を continuation の選択ヒントより優先し、そのヒントは参照しない。

focus は「今、認知リソースを割いて解決する対象」を示す。したがって focus 中は focus 外の Open Question を含む report も待つ可能性がある。focus session 内では内容上重要な Open Question であっても、別の優先階層や dispatch は設けず、到着順に沿って一連の batch として扱う。階層を増やすより、同一 session の report の流れを順に処理すれば十分という判断である。focus は既定 off とし、作業状況に応じて頻繁に切り替えたり解除したりする運用を想定する。

continuation は独立 queue や新しい優先階層ではなく、focus off のときにだけ session scheduler が参照する一回限りの選択ヒントとする。実装では既存の process-local `dispatchState` を使い、対象 session に ready batch がない間は消費せず、他 session を dispatch したらその session を次の直前対象とする。再起動時は reset する。これは最小実装上の選択で、operator が別途承認した永続化契約ではない。

これは一つの方針についての回答であり、ADR 全体の合意を示すものではない。ADR は引き続き `proposed` とする。

### 優先順位、公平性、待機上限、hold

- 以下は優先関係の全順序ではなく、既存契約・オペレータ回答・本 ADR の推奨案を区別する。

  | 条件 | session 選択の関係 | 根拠・状態 |
  |---|---|---|
  | TTY user input と watch report | TTY user input が先 | ADR 0037 の現行契約 |
  | 同一 session 内 | 到着順を維持し、後着の Open Question は先行する通常 report を追い越さない | オペレータ回答済み |
  | focus が on | TTY user input の後、ready な focus session の batch を focus 外 session の batch より report 種別を問わず先にする。continuation の選択ヒントよりも focus を優先する | `focus_all_reports`。inq-3 / inq-5 回答済み |
  | focus が off | TTY user input → Open Question を含む session → 直前 session の一回限りの選択ヒント（その session に ready batch がある場合）→ 到着順の tie-breaker | ADR 0037 の順序。inq-5 で focus off 時の適用を確認 |
| idle-only session batch が長く待った場合 | 低優先度で待ち、eligible 起点から5分後は通常 batch と同じ到着順 FIFO 帯へ昇格する。eligible後はhold中も時計が進むが、hold中は送信せず、解除時に経過 age で判定する。元の eligible / queue order と同順位 tie-break を保ち、TTY / OQ session / focus / continuation の選択順は越えない | 5分は operator-approved trial default、1〜30分は実装者 range。inq-13/14/15 の昇格・起点・manual hold中の時計とinq-16の候補生成 gate / refresh は承認済み。live session の確認範囲と freshness を含む観測境界は本 ADR の実装境界に記載 |
| idle candidate と通常 report が混在する shared batch | `highest_member_priority` を適用する。通常 report を含めば batch 全体を通常 priority として同じ batch / send で扱い、idle candidate は通常 report に同梱されて早く届く場合がある（hitchhiking）。batch は分割しない | inq-11 operator 承認済み。inq-16 の observable conversation / focus gate と解除後の一回限りの現状再評価も実装する |
| live OQ と idle candidate が同一 session にある | OQ が live であることだけでは候補生成を抑止しない。他の conversation / focus gate が閉じておらず idle 条件を満たせば候補を生成し、OQ report と同じ batch / send に到着順で含める。`highest_member_priority` により batch は OQ session の高い priority を保ち、OQ を追い越さず、OQ を重複生成しない | inq-17 operator 承認済み。focus gate が有効なら候補生成は引き続き抑止され、解除後に一度再評価する。lock 待ち中の append は現行 defect のため未保証 |

- `highest_member_priority` は batch 内の priority 集約規則で、既存の session scheduler 順位を置き換えない。TTY user input、focus の全 batch 優先、focus off 時の OQ session / continuation の順序は維持する。priority の集約で同一 session 内の FIFO や OQ 非追い越しも変えない。
- **inq-13 / inq-14 / inq-15 operator 決定（`promote_to_normal_only` / `age_from_eligible` / `age_during_manual_hold`）:** idle-only batch は operator-approved 5分 trial aging 後、通常 batch と同じ到着順 FIFO 帯へ昇格する。inq-14 により、時計は候補生成時ではなく、生成/dispatch gate を通過した候補が scheduler に載り、選択可能になった時点から開始する。gate により候補生成・scheduler admission が抑止されている期間は aging しないため、観測から候補生成・dispatch までの総時間に有限上限はない。inq-15 により、すでにeligibleな idle-only batch は manual hold 中も aging 時計を進め、hold 中は送信せず、nested / 重複holdが残る間はdispatchしない。昇格時に新しい順序を割り当てず、元の eligible / queue order と同順位 tie-break を保ち、age / order は refresh、append、retry、restart replay で reset しない。通常 scheduler が稼働し、到着率が処理能力を継続的に超えない場合、選択可能になった後は通常 batch の継続流入だけでは飢餓しない。aging は TTY user input、focus all reports、focus off 時の OQ session / continuation を追い越さず、process 停止中もdispatchしない。hold、process 停止、lock 競合、send retry、上位優先 class の継続がある場合の有限 dispatch deadline は保証しない。inq-16 により、候補生成前の observable conversation / focus gate 中は候補を作成・scheduler 登録せず、解除後に現稼働 session を一度だけ再評価し、条件を満たすものだけを新規生成・eligible にする。抑止中の候補蓄積や追いつき通知はせず、一時的な状態は通知されないことがある。この生成 gate は dispatch hold とは別であり、既にeligibleな候補は hold 中もagingするが送信しない。gate signal の出所・鮮度の扱いは #745 の generator で実装・確認する。
- `focus_all_reports` は Open Question の重要性を否定するものではなく、focus を「今、認知リソースを割く対象」として優先する選択である。優先の境界は session 間であり、同一 session 内では Open Question に追加の階層を設けず、到着順と一括配送を保つ。TTY user input を先に扱う現行契約は維持する。focus 中は focus 外の Open Question が待つ可能性があるため、focus は既定 off とし、状況に応じて切り替え・解除しやすくする。
- **inq-12 operator 決定（manual_clear）:** live 未回答 Open Question を観測しただけでは focus を自動解除しない。通常運用では、operator-agent とユーザが focus 対象 session との対話ターンを終え、その session が Open Question など人間応答待ちに入る際、operator / user が focus を手動で切り替えるか解除する。focus は対象作業が人間応答待ちに入った後も保持し続けない。既承認の10分 sliding inactivity timeout は、手動解除を忘れた場合の failsafe であり、通常手順や手動解除の代替ではない。worker report / watch update などの自動イベントは timeout を reset しない。一般的な worker 待ちや正常な長時間処理を自動推定して解除しない。「待ち」の追加判定方法や signal は未決の別設計事項とする。
- **同一 session の batch（operator direction）:** 同一 session の report は、可能な限りまとめて扱うことを優先する。通常 report と idle candidate を含む異種 report も原則として同じ session batch に載せ、到着順を保って同じ send で届ける。30秒 cap 到達時も report を分割せず、quiet window が短縮される後着 report を含める。サイズ制約、TTY / OQ / focus などの優先制約、lifecycle 上の具体的な技術理由により分割が必要な場合だけ例外とし、その理由と利用者への影響（追加 turn、順序、待ち時間、priority）を ADR / docs と該当 Issue の受け入れ条件に記録する。例外を理由に同一 session の到着順、同一 session 内での OQ 非追い越し、focus all reports を黙って変更しない。これらの契約に触れる必要が判明した場合は、別途判断を求める。
- **batch 集約待ち（30秒 cap は operator-approved trial contract）:** 現行の watch poll 2 秒 / `debounceMs` 250ms（0〜10秒）と message listen poll 2 秒 / `messageDebounceMs` 10秒（0〜120秒）は既存設定を保つ。session batch は最初の report を queue した `firstQueuedAt` を起点に30秒で ready にしてよい。report ごとの既存 `readyAt` / quiet debounce は残し、session 内で最も遅い `readyAt` と、batch 内で最も早い `firstQueuedAt + batchMaxWait` の早い方で batch readiness を決める。したがって scheduler の次回起床計算は、latest report の `readyAt` だけでなく `firstQueuedAt + batchMaxWait` も考慮する。cap 到達時に、quiet window が未満了の後着 report を含め同 session の batch を到着順のまま一つの `agent.send` で扱う。後着 report の通常 quiet window を短縮する場合がある。これは ADR 0078 の一括配送に batch readiness cap を加える変更であり、report / tranche には分割しない。30秒は operator 承認済みの調整可能な trial default、inq-18 承認済み範囲は10〜120秒。範囲内の変更でも batch は分割しない。`common.scheduling.batchMaxWaitMs` と profile ごとの `profiles.<name>.scheduling.batchMaxWaitMs` で調整し、説明には単位・default・min / max と集約 / 待ち時間への trade-off を記す。
- **ready 後・send 開始前の追記（inq-9 / inq-10 operator 承認済み）:** cap 到達などで batch が ready になった後も、send開始までは同一 session の後着 report を既存 batch に到着順で append し、追加 quiet wait なしで同じ send に含める。`firstQueuedAt` / cap はリセット・延長しない。実装上の freeze / send-start 境界は run loop での `commitBatch` 成功時とする。run loop は commit で report ID を in-flight に登録してから `await` なしで prompt を組み立て、send を呼ぶ。commit 時点でdispatcher queueに登録済みのreportを含め、それ以後の到着は次batchとする。peer process が共有stateへ保存済みでも、そのreportがcommit時点でprocess-local queueへ未同期なら次batchで扱う。inq-10で確定したこのlocal queue境界のため追加turnや待ち時間が生じうるが、後続batchでもFIFOを保ち report の欠落・誤帰属は許さない。send failure / unknown outcome では、`frozenBatchId` / `frozenPayload` を含む同じmembershipを retry / restart replayで保持し、後着reportを混ぜず同じ session の先行batchの後に扱う。append / payload split はbatch capとは別の技術例外とする。
- **idle-only fairness と優先度（5分 aging は operator-approved trial rule）:** hard wait は「ready になる」上限で、選択・send 完了の上限ではない。inq-13 で、idle-only batch は低優先度で待ち、5分 aging 後に通常 batch と同じ到着順 FIFO 帯へ昇格する `promote_to_normal_only` が承認された。inq-14 で aging 起点は、生成/dispatch gate を通過し、scheduler に載って選択可能になった時点と決まった。候補生成・scheduler admission が gate で抑止されている間は時計が始まらないため、観測から候補生成・dispatch までの総時間に有限上限はない。inq-15 で、すでにeligibleな idle-only batch の時計はmanual hold中も進み、hold中は送信せず、解除後に経過ageでpromotionを判定することが決まった。nested / 重複holdが残る間はdispatchできない。昇格時も元の eligible / queue order と同順位 tie-break を保ち、refresh / append / retry / restart replay で age / order を reset しない。通常 scheduler が稼働し、到着率が処理能力を超えない条件では、選択可能になった後は後着の通常 batch が継続しても aged idle-only batch は starvation しない。`highest_member_priority` により通常 report を含む混在 batch は通常 priority となり、idle candidate が同梱されて早く届く場合がある。aging は TTY input、focus all reports、focus off 時の OQ session / continuation の既存選択順を越えず、process 停止中もdispatchしない。hold、process 停止、lock 競合、send retry、上位優先 class の継続、または到着率が処理能力を超える場合の有限 dispatch deadline は保証しない。inq-16で承認された generation gate は、実装上 `agent.send` in-flight / pending submitted user input / conversation hold / active focus に対応する。watch pool は新しい UDS / saved-state observation だけを解除後の一回再評価に使う。manual report hold は eligible 後の dispatch hold として別扱いにする。未送信 TTY draft や一般的な worker / user wait は推測しない。
- **hold と deadline の実装:** batch readiness の `firstQueuedAt` / `readyAt` と eligible idle batch の aging は wall clock で進める。manual / conversation hold は dispatch を止めるが deadline 到達で自動解除しない。解除後は期限到達済み batch を選択可能にする。これは既存 `readyAt` の挙動と inq-15 の eligible idle aging 契約に沿い、hold 中の dispatch や有限 dispatch deadline は保証しない。focus/conversation generation gate は #745 が候補生成前に適用し、既にqueue済みの report hold とは別段階である。
- **選択順:** TTY user input は先。focus on では focus session の全 batch を focus 外より先にする。focus off では OQ session → continuation hint 一回 → 通常 / 昇格済み batch の到着順とする。idle 昇格は新しい通常 batch より先だが continuation hint より後とする。aging は OQ / focus / TTY を追い越さない。この案ではそれらが継続して到着すれば、low-priority report の dispatch に有限上限はない。
- **focus timeout（default は operator-approved trial。範囲は実装者の調整可能な初期案）:** focus は既定 off、単一 session を対象とする runtime state とし、process 内だけで保持して再起動時は off に戻す。operator / user の直接入力を滑動時計の起点・更新とし、worker report / watch update などの自動イベントでは更新しない。10分 default は承認済みで、3〜30分 range は利用者が調整するための実装者の初期案とする。`common.scheduling.focusInactivityTimeoutMs` または profile override で指定する。focus が人間応答待ちを越えて残る時間を抑えつつ、数回の agent turn を許容する値として10分を試す。実利用計測値はない。
- inq-12 で、live 未回答 Open Question の観測だけでは focus を自動解除しないことが決まった。focus 対象との対話ターンを終えて人間応答待ちに入る際、operator / user が手動で focus を切り替えるか解除する。10分 sliding inactivity timeout は解除忘れへの failsafe に限る。現行 `session.observe` の OQ snapshot は手動運用の手掛かりにはなるが、それ自体を自動解除 signal にはしない。`statusLine` や保存済み `running` phase から一般的な worker 待ちや正常な長時間処理を推定しない。その他の「待ち」の検出方法や追加 signal は未決である。
- **再起動と continuation:** profile-wide SQLite transaction 内で採番する単調な `arrivalOrder` と、pending report ごとの `firstQueuedAt` / `eligibleAt` を durable state に保存し、refresh / retry / restart replay で更新しない。successful `commitBatch` で同 batch の各 pending report に `frozenBatchId` と同一 `frozenPayload` を保存してから `agent.send` を呼ぶ。凍結後の replay は元の quiet `readyAt` を再適用せず、send 未完了時に保存した `retryReadyAt`（現行5秒 backoff）だけを待つ。retry 中は後着 report を別 batch に保ち、同一 session の先行 frozen batch が先に選ばれる。send success 後の ack-only retry は再 dispatch せず ADR 0082 に従う。旧 state の `queuedAt` は無視し、missing `firstQueuedAt` はその record の `readyAt` から初期化する。timestamp 専用 migration / backward-compatibility layer は設けないが、pending report ID / 内容の at-least-once 保持は維持し、再起動後に重複配送される可能性も残す。continuation は process-local の one-shot hint とし、ready batch がない間は消費せず、再起動時は reset する。focus も process-local で、再起動時 off とする。
- **send / ack 境界:** batch max-wait と aging は未 dispatch の queued report に適用する。send 未完了後の retry は同じ report ID / frozen batch membership と `firstQueuedAt` を保ち、既存の `retryReadyAt`（現行5秒 backoff）を早めない。cap 到達で batch が ready になっても、retry 中の send を5秒より前倒ししない。`agent.send` 成功後は ADR 0082 の ack-only retry に委ね、scheduler deadline で再 send しない。ack retry exhaustion や process 終了後は at-least-once replay により同じ ID が再送される可能性がある。
- Open Question の「優先」は、現行 hold 契約に従うなら**hold 解除後に、他の dispatch 対象と比べて先に選ぶ**ことを指す。hold 中にも例外 dispatch する案は ADR 0038 の「hold は全 watch report を保留する」契約を変えるため、独立した明示判断なしには採用しない。

### idle 通知の条件と重複抑制

- #745 の対象は、その operator-agent profile の manual watch と repository auto-watch に現在登録され、unique SessionResumeStore と reachable な live UDS observation が得られる session である。saved session 全体は走査しない。候補条件は idle phase と stale-running の二種類で、idle threshold / stale-running threshold は別設定とする。正確な進捗 heartbeat は取得できないため、`statusLine.reportedAt` は最終 status update の proxy として使い、worker progress の観測とは呼ばない。未知・stale・矛盾した状態は候補にしない。
- **inq-16 operator 決定（`suppress_then_refresh`）:** observable `agent.send` in-flight、送信済み operator input の pending、conversation hold、active focus の間は idle candidate を生成せず、scheduler に投入しない。gate 解除後は watch 対象を fresh poll し、その新しい観測から一度だけ現状を再評価する。抑止中に候補を蓄積したり、解除後に古い候補を追いつき通知したりしないため、一時的な状態は通知されないことがある。候補が新たに eligible となった時点から inq-14 の5分 aging を開始する。既にeligibleな候補はこの生成 gate の対象外で、inq-15どおり manual hold 中も aging する一方、hold 中は送信しない。一般的な worker wait、未送信 TTY draft、観測不能な user wait は gate として推測しない。
- **inq-17 operator 決定（`allow_with_oq`）:** live の未回答 OQ があることだけでは idle candidate の生成を抑止しない。他の conversation / focus generation gate が閉じておらず、idle 条件を満たす場合は候補を生成し、同一 session の OQ report と共有 batch / 同じ send に到着順で含める。`highest_member_priority` により混在 batch は OQ session の高い priority を保つ。idle candidate は OQ report を追い越さず、別 send に分割せず、OQ を原因とする duplicate OQ も生成しない。focus が active なら inq-16 の候補生成 gate は引き続き有効であり、live OQ だけでは focus を自動解除しない。operator / user が人間の応答待ちに入る際に focus を手動で clear / switch する運用を保つ。現行 observation は一般的な user-wait state を区別しないため、OQ の有無だけを user-wait gate に読み替えない。
- **inq-19 operator 決定（`include_stale_running`）:** idle-phase candidate に加え、live UDS observation で現在 `running` と確認できる session も対象にする。`statusLine.reportedAt` が60分以上前なら「60分以上更新なし・要確認」として候補にし、異常・停止とは断定しない。statusLine の本文と最終報告時刻を表示する。statusLine が現在の running phase より前の報告でも最後に観測した報告として扱う。worker progress heartbeat はないため、statusLine は最終 status update の proxy にとどまり、実作業の進捗への正確な signal mapping は未解決のままである。欠落 / future timestamp は候補根拠にしない。長時間の正常処理はあり得るので確認の促しにとどめる。idle phase の閾値は別に operator が決めた30分を使う。候補対象は実装上 watch pool の範囲に限り、保存 session 全体や全 live session の網羅性は保証しない。
- **inq-20 operator 決定（`idle_threshold_30m`）:** #745 の `harnessPhase=idle` 候補は30分を初期 / default threshold とする。これは調整可能な設定で、10〜120分は実装者が採用する初期調整範囲であり、operator が選択した追加条件ではない。30分未満では候補を出さず、経過時間を長くすると候補頻度が下がり、短くすると候補が早まる。`running` の60分条件とは別に適用する。
- **#745 の初期設定と signal 境界（実装上の調整可能な trial）:** idle-phase threshold は30分 default / 10〜120分、stale-running threshold は60分 default / 30〜240分、candidate reevaluation は1分 default / 30秒〜5分、idle aging は5分 default / 1〜30分とする。10分 focus inactivity timeout / 3〜30分も設定可能とする。batch max-wait は operator 承認済み30秒 default / 10〜120秒である。batch 以外の range は既決条件と既存の2秒 watch poll を基にした実装者の試用範囲であり、operator が個別に承認した値ではない。設定は `common.scheduling.<field>` と `profiles.<name>.scheduling.<field>` に置き、profile は項目単位で上書きする。既存 per-watch / per-listener poll と debounce はこの設定と別に保つ。
- #745 generator は、明示 observation を `(value, source, observedAt, freshness)` として扱う。`harnessPhase` / `modifiedAt` は SessionResumeStore の保存 state、`session.observe` は reachable な live UDS から得る session / OQ / statusLine 証拠として出所を区別する。`modifiedAt` は phase transition 専用 timestamp ではなく、最新 harness activity / phase transition の時刻である。poll 前後に phase state を読み直し、phase / modifiedAt / lifecycle が変わった場合や missing / stale / conflicting observation は unknown として候補にしない。stale-running の根拠には `statusLine.reportedAt` を「最終 status update 時刻」の proxy としてのみ使い、worker progress と主張しない。statusLine 欠落 / future timestamp は根拠にしない。freshness は watch poll interval の2倍以内（最低10秒以内）。正常な長時間処理や一般的な user wait を異常と推定しない。
- idle priority と候補生成 gate は別段階である。inq-11 の `highest_member_priority` はeligibleになった idle candidateを共有 session batch 内で扱い、通常 report を含む batch は通常 priority になる。inq-17 により live OQ report と同梱される候補は OQ session の優先度を保ち、arrival order に従って同じ send で届く。inq-16 の gate は candidate を scheduler に載せる前に働き、manual report hold や eligible 後の inq-15 aging / dispatch 停止を置き換えない。独立 batch は既定にしない。
- idle candidate reevaluation cadence は #745 の1分 default / 30秒〜5分 range とする実装者の trial で、scheduler batch readiness deadline とは別の時計である。gate 解除時の一回 refresh は周期再評価に加えるが、抑止中に蓄積した候補の catch-up はしない。scheduler の batch max-wait はすでに queue 済み report にだけ作用し、候補生成前の idle 時計や観測から候補生成までの総時間に上限を設けない。
- **idle 候補と shared batch（operator direction）:** idle candidate も同一 session の通常 report と共有 batch に含め、batch は分割しない。inq-11 で `highest_member_priority` が承認され、通常 report を含む batch は通常 priority となって idle candidate が同梱され早く届く場合がある。inq-17 で live OQ だけでは候補生成を抑止せず、他の generation gate が開いていて idle 条件を満たせば、候補を同一 session の OQ report と同じ batch / send に arrival order で含めることが決まった。混在 batch は OQ session の優先度を保ち、OQ の追い越し・別 send への分割・OQ の重複生成をしない。focus が active な間は inq-16 gate が候補生成を抑止し、解除後の一回再評価では OQ がまだ live でも候補化できる。focus は OQ だけで自動解除せず、人間応答待ち前に operator / user が手動 clear / switch する。idle evidence が OQ と同じ batch で届き、早く通知される場合があることを docs に説明する。idle-only batch には5分 aging / 低優先度規則を適用する。通常の選択経路で OQ と候補が batch 選択前に同一 process-local queue に揃った場合は結合できるが、profile lock 待ち中の append は #741 の既知 defect により保証対象外である。独立 queue / ack 経路や別 batch を既定にしない。
- #745 は同じ fingerprint の候補を、観測 evidence が変わるまで再生成しない。trial 中は定期 reminder timer を設けない。候補再評価 cadence は1分 default / 30秒〜5分 range とし、同一 fingerprint の再通知間隔は別時計として追加しない。candidate kind ごとの fingerprint state は既存 profile watch state に durable に保持し、ack / restart 後も同じ根拠の再生成を抑止する。pending report ID / ack state は別に既存 lifecycle で保持し、fingerprint 更新で pending report を置換・削除しない。
- pending report の retry / ack / restart replay は既存 lifecycle を使う。再起動や ack retry exhaustion 後には同じ report ID が再送される可能性があり、at-least-once の重複可能性は残る。これは fingerprint による同じ根拠の再生成抑止とは別の境界である。

### 再起動・失敗時の期限と配信

- 現行 `readyAt` は peer refresh / restart で再利用されるが、batch の最初の待ち始めは保存されていない。operator 承認済みの30秒 batch max-wait では、新 state に各 pending report の `firstQueuedAt` を保存し、未凍結 session batch はその最小値から max-wait を計算する。各時刻は refresh / retry / restart を越えて保持する。旧 state の `queuedAt` は無視または再設定してよく、その timestamp 専用の migration / backward-compatibility layer は設けない。旧 timestamp の扱いは pending report 自体の ID / 内容を at-least-once replay 対象として保持することと区別する。
- hard deadline の対象は未 dispatch の queued report batch である。batch を ready にする期限は、session 内の latest report `readyAt` と、batch 内で最も早い `firstQueuedAt + batchMaxWait` の早い方とし、scheduler の次回起床計算にも両方を含める。send 未完了の retry と再起動 replay では新 state の `firstQueuedAt` を維持する。`agent.send` 成功後は scheduler deadline で再送せず、ADR 0082 の ack-only retry 契約に従う。
- hard deadline が保証するのは、動作中 scheduler が queued batch を ready にできることまでであり、実 dispatch / send までの有限時間ではない。process 停止中、lock が繰り返し取得できない間、`agent.send` 中や中断中、明示 hold 中、TTY user input / focus / Open Question の優先対象が続く場合の dispatch 時間は保証しない。ack retry exhaustion や restart replay では at-least-once により重複しうる。

### 設定・操作面と Issue の作業範囲

- **focus 操作面:** focus は既定 off、TTY の `/focus <conductorAgentId>` / `/focus-off` と `set_session_focus` tool から同一 process-local state を操作する。`/focus` は現在値を表示する。timeout default 10分は operator-approved trial、3〜30分は調整可能な実装者 trial range とし、`common.scheduling.focusInactivityTimeoutMs` と profile override で設定する。operator / user の TTY 入力が sliding clock を更新し、agent tool invocation、自動 report / watch event は更新しない。TTY の focus command は入力 ingress 側で時計を更新してから focus state を切り替える。再起動で focus は off に戻る。help / tool description は default off、focus 外 OQ が待つ可能性、human-wait 前の手動 clear / switch、timeout が解除忘れ時だけの failsafe であることを説明する。
- **focus の解除方針（inq-12 operator 決定）:** live 未回答 OQ の観測だけで focus を自動解除しない。focus 対象との対話ターンが終わり、人間応答待ちに入るときは operator / user が手動で切替・解除する。10分 sliding inactivity timeout は解除忘れに備える failsafe のみとする。一般的な worker 待ちや正常な長時間処理を自動で待ちと判定して解除する方式、追加 signal の有無は未決である。
- TTY と agent tool の focus 操作は同じ runtime scheduler state を変更し、別々の設定値・永続状態を持たない。scheduler / idle 関連値は `operator-agents.config.yaml` の `common.scheduling` と `profiles.<name>.scheduling` にまとめ、profile は項目単位で override する。既存 watch ごとの `debounceMs` / message listener の `messageDebounceMs` は維持し、同じ値を別の面で重複設定しない。
- **オペレータ指示済みの利用者説明要件:** help / tool description / 該当 prompt には、priority の意味、focus 外 OQ が待つ可能性、focus の default off・頻繁な切替/解除、focus 対象との対話を終えて人間応答待ちに入る際の手動切替・解除、10分 sliding inactivity timeout は解除忘れ時の failsafe であることを説明する。最後の operator / user 入力だけが timer を更新し、`set_session_focus` の呼び出し、worker report / watch update 等の自動イベントは reset しないことも記す。一般的な待ちを自動検出して解除する契約は説明・実装済みと扱わない。
- inq-6 / inq-7 の operator 承認により、native hierarchy は Epic #748 → #741 → #745 とする。#741 は共通 scheduler、#745 は idle 候補の生成・判定・根拠・gate・重複抑制を担い、共有 dispatcher と通常 report lifecycle に依存する。#745 では低優先度や継続更新だけによる starvation を避ける境界・例外、hold / 停止 / 再起動時の pending 候補・重複抑制状態と at-least-once 重複可能性を設計・説明する。idle 定期生成時計は scheduler の queued report deadline と別に保ち、独立 queue / ack 経路を前提にしない。

## #745 の実装境界と観測範囲

Operator の inq-20 により `harnessPhase=idle` threshold は30分 default として固定され、これは調整可能な値である。#745 は 10〜120分の調整範囲、`running` の60分 threshold / 30〜240分範囲、idle aging の5分 default / 1〜30分範囲、1分 reevaluation cadence / 30秒〜5分範囲を実装者 trial として採用する。これらの range は implementer が理由を添えて採用した調整範囲であり、operator が個別に選んだ値ではない。意味・単位・default・範囲・効果は利用者向け docs に記載する。

候補対象は profile の manual watch と repository auto-watch が選んだ稼働候補に限り、全保存 run や全 live session の網羅は保証しない。auto-watch は profile あたり最大20 run である。候補には一意な SessionResumeStore、reachable な UDS observation、観測と整合する `harnessPhase` / `modifiedAt` が必要で、UDS snapshot の前後に phase state を再読込して変化を確認する。freshness は configured watch poll interval の2倍以内（最低10秒）とする。terminal / missing / stale / conflicting / fallback-only observation は unknown として候補から外す。

idle-phase candidate は `harnessPhase=idle` かつ `modifiedAt`（最後の harness activity / phase transition 時刻）が threshold 以上前の場合に作る。`modifiedAt` は idle phase entry 専用時刻ではなく、他の harness state write で起点が新しくなる場合がある。stale-running candidate は現在の live phase が `running` で、statusLine の `reportedAt` が stale-running threshold 以上前の場合に作る。worker progress heartbeat は存在しないため statusLine は last-status-update proxy として表示し、worker progress と呼ばない。statusLine が running phase より前でも最終 report 時刻として扱うが、欠落 / future timestamp は根拠にしない。長時間の正常処理や一般的な user / worker wait は異常と断定しない。

observable generation gate は operator-agent `agent.send` in-flight、pending submitted user input、conversation hold、active focus である。active 中は候補を作成・scheduler admission せず、解除後は全 watch 対象を fresh poll して一度だけ現状を再評価する。busy 中の状態を backlog 化しない。live OQ 単独は gate ではなく、OQ と idle candidate が選択前に同一 session queue に揃えば arrival order で同じ batch / send に含め、OQ priority を保つ。manual report hold は generation gate と別で、eligible candidate の aging は進めるが送信は止める。

fingerprint state は既存 profile watch state に session / candidate kind ごとに永続化し、idle phase の `modifiedAt`、stale-running の harness state update 時刻と statusLine / `reportedAt` を根拠にする。同一 fingerprint は ack / restart 後も再生成せず、evidence が変わった場合に新候補を作る。report ID、frozen batch、retry、ack は既存 pending report lifecycle を使い、再起動・ack retry exhaustion・複数 process 競合で重複配送しうる at-least-once 境界は残る。

## Consequences（提案段階）

#741 は既存 pending report queue と report ID ごとの ack lifecycle を使い、独立 queue / ack path を作らない。`batchMaxWaitMs` は最初の `firstQueuedAt` と既存 quiet `readyAt` の早い方で batch を ready にし、scheduler wakeup も両方の期限を考慮する。これは ready 化の上限で、実際の dispatch deadline ではない。30秒 default と10〜120秒 range は operator 承認済みの調整可能な trial 契約である。quiet window を短縮する場合も batch を分割せず、同一 session 内を到着順で同じ send に含める。

受け入れ済み append cutoff 契約は、成功する `commitBatch` 時点までに process-local queue に届いた同一 session report を含めて membership / payload を freeze することである。一方、現行実装は shared queue membership を profile lock 待ちの前に freeze するため、lock 待ち中に届いた report は commit 成功より前でも同 batch に入らない。この差は #741 reviewer が指摘した未解決 defect として扱い、#745 は `commitBatch` / shared scheduler を修正しない。lock 待ち中の OQ + idle candidate 同一 send は保証済みと扱わず、#741 側の修正後に結合検証する。

commit 前に同一 queue に揃った report の frozen batch は、durable manifest / payload を保存後に send する。persist failure 時は send せず捕捉した report を queue に戻す。commit 後の到着は次 batch とし、send failure / unknown outcome では同じ `frozenBatchId` / `frozenPayload` で retry して後着 batch を先行させない。frozen batch は quiet `readyAt` を再適用せず、retry が必要な場合だけ `retryReadyAt` を使う。`firstQueuedAt`、`eligibleAt`、`arrivalOrder` は retry / restart replay で保持する。旧 state の `queuedAt` migration は行わず、missing `firstQueuedAt` は `readyAt` から初期化する。pending report の at-least-once 保持、ack-only retry、重複配送の可能性は ADR 0081 / 0082 に従う。

selector は TTY input の後、focus on なら focus session の全 batch、focus off なら OQ session、one-shot continuation、通常 FIFO の順を守る。idle-only batch は eligible 起点から5分後に通常 FIFO 帯へ昇格するが、この昇格は TTY / focus / OQ / continuation を追い越さない。eligible 後は manual hold 中も aging する一方、hold 中と process 停止中は dispatch しない。通常 report の継続流入による starvation は、scheduler が動作し処理能力を超える backlog が続かない範囲で避ける。hold、停止、lock contention、send retry、上位 priority の継続を越える有限 dispatch deadline は保証しない。mixed batch は `highest_member_priority` を採り、通常 report を含むと idle candidate が同梱されて通常 priority で早く届くことがある。live OQ と idle evidence が commit 前に local queue に揃っていれば一つの batch / send に到着順で含め、OQ priority を保つ。future candidate を待って OQ を遅らせない。

focus は既定 off で、TTY `/focus` controls と `set_session_focus` tool は同じ process-local state を操作する。最後の operator / user 入力から10分で解除する sliding timeout は解除忘れ時の failsafe であり、worker / watch event は timer を更新しない。focus 対象が human-wait に入る際の通常操作は手動 clear / switch とする。focus target に一般的な worker wait / 長時間処理を推測して自動解除しない。reboot 後 focus は off、continuation hint は reset する。

scheduler / focus / idle の設定は `common.scheduling.<field>` と `profiles.<name>.scheduling.<field>` を使い、profile override は field-wise とする。既存 per-watch / per-listener poll / debounce 設定は別に保つ。試用値は batch max-wait 30秒 / 10〜120秒、idle phase 30分 / 10〜120分、stale running 60分 / 30〜240分、idle aging 5分 / 1〜30分、focus timeout 10分 / 3〜30分、idle reevaluation 1分 / 30秒〜5分である。batch range と operator 決定の閾値/default は明示的に承認済みで、batch 以外の range は理由を添えた実装者 trial であり operator が個別選択した値ではない。idle candidate generation / evidence / gate / fingerprint は #745 の責務であり、本 Issue の shared scheduler 実装には含めない。

## #745 と shared scheduler の境界

#745 の候補生成は watch pool の live UDS snapshot と persisted phase / statusLine evidence を使い、unknown evidence は候補にしない。candidate cadence、phase threshold、fingerprint / generation gate は #745 の責務である。queued report の batch readiness、priority / aging / focus / continuation、hold / retry / ack は #741 の shared scheduler と既存 pending report lifecycle の責務であり、#745 は独立 queue / ack 経路を追加しない。#741 の append cutoff defect が修正・検証されるまで、lock-wait 中に到着した同一 session report の同一 send は未保証のまま残る。
