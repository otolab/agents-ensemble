# 設計の大原則

## 何を作るか

- コマンド名: **`ensemble`**
- 最小ユースケース: Issue を指定して起動 → worker / reviewer を起動して作業
- 権限・方針の問題: Issue に記載して回答を待つ、または CLI でユーザーに最小限問い合わせ

## 原則

1. **エージェントシステム** — 内部の規定をがっちり作らない
2. **Skill 依存** — 作業・レビュー・オーケの各 Skill が手順と判断の正本
3. **自然言語ベース** — 起動プロンプト、Skill 本文、必要なら Issue 上の報告様式
4. **Issue / PR / ファイル**で情報共有（セッション会話に依存しない）
5. **オーケの遷移判断は機械化しない** — フル Agent が Issue/PR を読んで決める
6. **作業基準文書は外から都度与えられる** — 形式固定しない。オーケの判断材料として渡す

## 固くしないもの

- 内部状態のスキーマ（`WORKFLOW_*.md` のフォーマット固定など）
- フェーズ遷移のルール表・機械可読トリガー
- dispatch レジストリの厳密な型

## 与えられるもの（入力）

- 各種 **Skill**（共通）
- **作業基準文書**（フロー / Issue ごと、自然言語）
- **Issue / PR**（事実・履歴）
- Issue で**最終報告の形**を決めることはあり
