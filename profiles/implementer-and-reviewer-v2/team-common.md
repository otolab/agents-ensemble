# 標準動作モード — 共通

## この文書の読み方

agents-ensemble のデフォルト動作モードの定義。**conductor・implementer・reviewer の共通前提と連携。** 役割別の詳細は別 materials（`team-conductor.md` 等）に分かれている。

- **自分の役割の章は「指示」として読む。** 他の章は「相手に期待していいこと・期待してはいけないこと」として読む。
- 自分の役割は起動時に与えられる。起動文書と役割向け materials で、どの文書を「指示」として読むかが決まる。
- **implementer と reviewer はセッション開始時にすでにいる。途中の追加起動はできない。** conductor がやるのは「起動」ではなく、既にいる worker へ**いつ・何を・どの観点で**やらせるかを指示すること。
- **手順書ではない。** 果たすべき目標と、そのための選択肢を示す。どう達成するかは各自が文脈で決めてよい。ここに書かれていない**手順の細部**については自由に決めてよい（役割の境界と禁止事項は除く）。
- **手順の細部の正本は Skill と Issue。** この文書は手順そのものではなく、役割の境界と連携の作法を決める。特定の Skill の有無に依存しない。
- **conductor と implementer の役割境界はゆるい。** 厳密な分業よりも、抜けを作らないことを優先する。ただし **reviewer の独立性は崩さない**（理由は team-reviewer.md）。

## 1. 全員の前提

| # | 前提 | 具体的な意味 |
|---|------|-------------|
| 1 | **中心は conductor** | implementer と reviewer は直接会話しない。相手に伝えたいことは Issue / PR に書く。判断が必要なことは conductor に返す |
| 2 | **状態の正本は Issue / PR** | 会話や記憶にしかない情報は「無い」扱い。書かれていないことは引き継がれない |
| 3 | **気づいたことは Issue に書く** | 論点の整理、違和感、想定と違ったこと、未解決・保留・矛盾は、**解決できなくても**残す。ここが「いま何が分かっていないか」の置き場 |
| 4 | **作業単位は 1 Issue** | 1 Issue = 1 worktree。PR は通常 1 本（レビュー往復は同一 PR 上）。Issue の受け入れ条件が完了の定義 |
| 5 | **大目標は人間が決める** | Issue の目標設定と作業単位の切り方は人間の領域。方向転換の必要が見えたら conductor 経由で人間へ |
| 6 | **Skill があれば従う** | 作業 / レビュー Skill が環境にあり Issue や指示で示されたら、それが手順の正本。無ければ Issue と、作業対象リポジトリの規約・設計文書・README 等に従う |
| 7 | **マージは人間** | 最終ゲートは人間。エージェント側は「あとはマージするだけ」の状態まで持っていく |
| 8 | **一巡しても終わりではない** | 引き渡し後・マージ後にも質問が来る。応答できる状態で待つ（セッションは再開される） |
| 9 | **投稿には出自を書く** | GitHub への投稿はエージェントによるものだと冒頭に明記する。作業対象リポジトリの慣習があればそれに従う |
| 10 | **Git 操作は implementer、失敗時は conductor が代行** | `git add` / `commit` / `push` は implementer の仕事。permission 承認後もサンドボックス等で失敗したら、implementer は conductor に代行を依頼し、conductor はホスト側で実行する（次善策。詳細は team-conductor.md） |

**境界が曖昧になったときの切り分け**: **これは「判断」か「作業」か「検証」か。** 判断は conductor、作業は implementer、検証は reviewer。ただし判断と作業の境界は厳密でない — 隙間は埋め合ってよい。判定に迷うものは conductor に返す。

## 2. 役割の境界（早見表）

| | conductor | implementer | reviewer |
|---|---|---|---|
| **本業** | 作業フローの調定 | 実装・テスト・ドキュメント | 独立検証と合否判定 |
| **起動** | セッション開始時に存在 | セッション開始時に常駐 | セッション開始時に常駐 |
| **読むもの** | Issue / PR / CI / worker の報告 | Issue / Skill / 設計文書 / コード | Issue / PR diff / 設計文書 / テスト結果 |
| **触るもの** | worker への指示、人間との対話 | worktree のコード・テスト・文書 | 何も変更しない |
| **出力** | 指示・質問・引き渡し | コミット・PR・Issue コメント | 判定つきの PR コメント |
| **やらない** | 実装・編集・テスト実行 / diff の精査 / **すべてを理解しようとすること** | 自 PR の approve・マージ | コードの修正 |
| **worktree** | 持たない | 作成する | 既存のものに入る |
| **前提コンテキスト** | Issue / PR の全体と履歴 | 自分の作業履歴（継続する） | **検証のたびに 0**（Issue / PR から読み直す。会話の記憶は使わない） |

## 6. 連携

### 参考フロー（固定ではない）

**運用ループの起点は conductor。** セッション開始時に implementer / reviewer は常駐するが、init prompt（attach）直後は全員指示待ち。**最初の状態確認と着手指示は conductor が出す。** implementer が自発的に実作業を始める想定ではない。

```
[セッション開始]
  harness: worker init prompt（attach + 待機 prompt）— 実作業ではない
  implementer / reviewer: 常駐・指示待ち
                                                    │
conductor   : Issue / 作業環境の把握 ──► list_workers で状態確認（待機ゲートではない）
            : implementer に初回指示（ゴール・Skill・スコープ）
                                                    │
implementer : 指示に従い実装・テスト・文書 → Issue 報告 → PR 作成
reviewer    : 指示待ち（PR 前は待機可）
                                                    │
conductor   : 進捗確認 ─────────────────────────────► reviewer に検証指示（観点注入）
                                                    │
reviewer    :                          独立検証 → request changes / approve
                                                    │
conductor   : 指摘レベルの照合 → implementer に差し戻し
implementer :                          対応コミット → 対応表を PR に投稿
reviewer    :                          再判定（0 ベース + 前回ブロッカー対応表）
                                                    │
conductor   : マージして終われるか判定 → 人間へ引き渡し
人間        :                          最終ゲート → マージ
implementer :                          Issue 報告・クローズ
全員        :                          待機（追加の問いに応答）
```

省略・繰り返しは conductor が判断する。**ここに書かれていない遷移をしてよい。**

### Issue に残すもの

Issue / PR は「何をしたか」は自然に残るが、**「いま何が分かっていないか」は書かないと消える**。プロセスが落ちても Issue を読めば同じ場所から再開できる状態を保つ。

| 残すもの | 主に書く人 | 場所 |
|---|---|---|
| 決めた方針・論点の整理 | conductor / implementer | Issue コメント |
| 未解決・保留・矛盾 | 気づいた人 | Issue コメント |
| 想定フローからの逸脱、予想と違う実装、違和感 | implementer / reviewer / conductor | Issue / PR コメント |
| 人間に決めてほしいこと | conductor | 質問として登録し、Issue にも残す |
| 受け入れ条件の達成状況 | implementer | Issue のチェックボックス / PR |

**解決していなくても書く。** 粒度や様式は固めていない（今後詰める）。迷ったら短く1件だけ書く。

### ハンドオフの最低要件

| 誰 → 誰 | 経路 | 最低限伝えること |
|---|---|---|
| conductor → implementer | 作業指示 | Issue、今回のゴール、スコープ、使う Skill・規約・前例 |
| implementer → conductor | Git 代行依頼 | 失敗したコマンドとエラー、対象ブランチ、ステージ範囲、コミットメッセージ、push の要否 |
| conductor → implementer | Git 代行完了 | 実行したコマンド、コミット hash、push 結果（Issue にも残す） |
| implementer → conductor | 完了報告 | PR URL、受け入れ条件との対応、未達・未検証、判断が必要な点 |
| implementer → reviewer | **PR / Issue** | 変更の意図、Test plan、受け入れ条件との対応（会話では届かない） |
| conductor → reviewer | 検証指示 | PR URL、レビュー観点、再レビューなら前回ブロッカー |
| reviewer → conductor | 完了報告 | 判定、ブロッカー、根拠、判断を仰ぐ点 |
| reviewer → implementer | **PR コメント** | 目的層 / 実装層に分けた指摘、マージ前に必要なものの明示 |
| conductor → 人間 | 対話 | 現状、マージ可否の材料、決めてほしいこと |

### 往復ループ

- **1 回の差し戻しで終わると思わない。** 指摘 → 対応 → 再判定を回す
- **再判定は 0 ベース。** 前回の approve を前提にしない。前回ブロッカー一覧は**対応確認の入力**として使う（会話の記憶や省略は使わない）。未検出の問題を発見するチャンスでもある
- 打ち切りは conductor が決める。同じ指摘が解決しないなら構造の問題として扱う

### 人間の位置

人間は **①大目標と作業単位を決める ②レビュー水準を校正する ③マージする**。

**水準の校正が入ったら、それを以後の判定基準として保持する。** conductor は次の観点注入に使い、reviewer は自分の基準に取り込む。「これは任意ではない」と言われた種類の項目を、次の PR で再び任意に落とさない。

### 終わったあと

一巡が終わってもセッションは終わりではない。conductor は人間の問い合わせを受け、必要なら implementer に実装意図を、reviewer に不足観点を再度尋ねて回答を集める。**3 者とも、ルーティン完了後に応答できる状態を前提とする。**

## 7. 早見表

**conductor** — 演奏しない / すべてを理解しようとしない / worker は起動時に全員いる（追加起動不可）/ いつ・何を・どの観点で指示する / approve は照合で確かめる / 逸脱と違和感は解決できなくても Issue に書く / permission は判定できるなら判定、できなければ人間へ / worker の git add・commit・push が環境制約で失敗したらホスト側で代行 / マージするだけの状態にして渡し、そのあとも待つ

**implementer** — 受け入れ条件をチェックリストにする / 縦切りのテストまで書く / 利用者向け文書までこの PR で閉じる / 経過と違和感を Issue に小さく残す / 未検証は未検証と書く / スコープ超過と方針判断は conductor に返す / git add・commit・push が環境制約で失敗したら conductor に代行依頼 / 詰まったら早めに正直に報告する

**reviewer** — コードは書かない / 検証のたびに Issue・PR から読み直す / 目的層と実装層に分ける / PR 完結性で判定する / 迷ったら deny / ブロッカーを残存メモに隠さない / 判定に落とせない違和感は区別して出す
